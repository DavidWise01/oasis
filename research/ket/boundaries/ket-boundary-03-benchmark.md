# KET Boundary 03 — Incremental checkpointed ledger

Date: 2026-10-22  
Implementation: `research/ket/boundaries/ket-boundary-03.html`

## What changed from Boundary 02
- Incremental append hashes only the latest entry, checks prior head before new commit and checks postwrite head. Full O(n) chain validation occurs at recovery and explicit checkpoint.
- Explicit local ECDSA P-256 SHA-256 checkpoint signing; public/private key pair generated by WebCrypto. Verification compares signed checkpoint with journal prefix, catching modification or truncation when the checkpoint/key reference is retained.
- Duplicate identity returns REPLAY; a packet is never sent externally in this prototype.
- Keeps frozen token `{{ -+001122334455667788990099887766554433221100-+ }}`, 488-address routing, 256 mirror mapping, independent 8×3 register.

- Total checks: **128 passed** (120 commits, token, valid hop route, full validation, anchor verification, duplicate, tamper, truncation, modified-signature payload).
- Mean transaction: **0.621 ms**; median **0.483 ms**; first **1.058 ms**; last **0.483 ms**.

- The benchmark excludes rendering, localStorage I/O, page lifecycle, concurrent tabs, and network effects.

## Security and recovery limitations
- Current browser signs with an extractable ECDSA private key **stored in the same localStorage origin** as the journal, so a local attacker can replace all of them. This is an integrity demonstration, **not independently anchored authenticity**.
- Snapshot overwrite/storage quota/concurrent tab writes are not crash-safe transactional storage or distributed exactly-once semantics.
- A tampered middle entry is detected on full recovery validation; incremental appends check only the current head and trust a previously recovered journal.
- Checkpoint signing is manual; users must export/preserve signed checkpoints and **public key in an independent trusted place** to obtain stronger externally verifiable provenance.
- The reported simulated HOLD is based on expected/actual flags, not proof that an external proposition is true.
- No browser UI test was completed here; JavaScript syntax and Node.js core tests passed.

## Engine trajectory
**Governed event-sourced provenance and receipt kernel.** The natural next boundary is transactional storage (IndexedDB), independent public-key anchor/export, multi-tab concurrency control, and a formal append-only verification protocol.
