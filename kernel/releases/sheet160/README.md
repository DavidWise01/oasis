# OASIS SHEET 160 — Durable Indexed Merkle Segment Store

**Status:** `0e / PASS` for 71 core fault checks, 19 certified-history migration checks and a 12,288-record indexed-storage benchmark. The inherited SHEET 159 chain was attempted but timed out near SHEET 148; see `combined-run.log`. The baseline `baseline159/` is an unmodified full snapshot.

## What changed

The witness-history scaling blocker in SHEET 159 was a full-history JSON reload and `S151.accumulate` / `S151.extension` scan on every proof request. SHEET 160 supplies an **additive** indexed physical Merkle store that retains the exact binary-peak Merkle hash convention from SHEET 151: indexed leaves use `S151:LEAF` with absolute record indexes, internal nodes use `S151:NODE`, and peak bagging uses `S151:BAG`. The new read path no longer regenerates historical hashes on a proof query.

An active segment holds up to **256 records** and its local dyadic subtree hash index. Each complete segment contributes its 256-leaf root to a persistent upper-level index, which stores larger aligned 512/1024/2048/etc. blocks. The head stores count, Merkle frontier/root, lastRecordHash, and a SHA-256 digest of each physical segment. Proof generation resolves O(log N) subtree hashes via these persisted indexes. Only the requested segment files need opening; a signed external head checkpoint can be verified separately.

The local write sequence is segment write -> fsync -> atomic rename -> global head write -> fsync -> atomic rename. An interruption after the segment write leaves a detectable quarantine state. Restoration needs signatures from two distinct Ed25519 operators authorizing the **specific orphan hash and previous head digest**. The record is not written a second time. If the head was already committed but the acknowledgement failed, retrying the same expected index and payload returns the original record.

## Measured workload

`bench160.js` appends **12,288 real records**, crossing 48 physical segment boundaries, and verifies 250 indexed inclusion and nine consistency proofs against the stored Merkle root.

Measurements are from one ephemeral local container, not a throughput guarantee. This is a synchronous, fsync-heavy JSON-backed demonstration—not a production database.

## Compatibility

`importWitness()` accepts the existing SHEET 159 witness history and **two distinct signed SHEET 159 Merkle checkpoints**, validates every original witness hash link and exact certified root, then creates a separate indexed store via atomic directory rename. The first 519 migrated witness leaves and their root remain unchanged. A subsequent native transaction was appended as record 520, and the full audit passed. Existing SHEET 159 code is not changed or transparently replaced.

## Safety and engineering boundaries

1. These are **indexed subtree proofs**, while transferring a missing suffix still costs O(missing data). The current physical store writes 256-row JSON segments, not an LSM database or a network sharded store.
2. `read()` validates the head and last segment; historical segments are authenticated **on access**, while `verifyFull()` performs a deliberate linear forensic scan. A trusted, independently retained signed head is necessary to detect coherent local rollback of head and segment bytes. The demo does not operate an independent witness for this new store.
3. The orphan reconciliation mechanism uses two authorizing keys provided by the test harness. It is **not** yet integrated with the deployed remote authority quorum, and a local filesystem lock cannot establish cross-host mutual exclusion.
4. The inherited SHEET 159 regression chain exceeded this run's execution limit around SHEET 148. The prior SHEET 159 release had a full run with exit 0, but that does not count as a fresh SHEET 160 combined pass. The old SHEET 142 concurrency race remains unresolved.
5. No claim is made about power-loss behavior of hardware caches or independenty hosted consensus; testing used one container/host.
